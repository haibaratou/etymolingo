## 最初に読む：担当と完成条件

1. **担当1：単語からプロンプトCSVを作る。** 正本の代表的な第一語義・正確な語の識別・正式画像名を確認し、具体的な画像生成プロンプトを保存する
2. **担当2：CSVから画像を生成し、検品し、CSVを更新する。** 実際に送ったプロンプト、生成結果との対応、実PNG、短い英日解説、検品結果を同じ行に残す。今画像を生成しているCodexもこの担当に当たる
3. **反映バッチ：検品合格行だけを辞書原本へ取り込む。** 画像・解説を正確な語と第一語義に結び付け、正本保存後に公開データを書き出す。CSVを保存しただけでは原本反映・公開完了にならない

この改訂は制作手順・CSV仕様の改訂。CSVから原本へ安全に一括取り込みする専用コマンドは、現時点のリポジトリには未実装。既存の書き出しコマンドと、必要な取り込み処理を末尾で区別する。

合格の基準は **代表的な第一語義・採用実画像・英日解説の三者が自然に一致すること**。画像だけで英単語の綴りや活用形を一意に当てられることは要求しない。画像に合うように語義を変更・並べ替えたり、説明で意味の食い違いを隠したりしない。

現在の画像を判断材料から外して、信頼できる辞書と現代の自然な用法から代表語義・品詞・見出し語の形を確認する。辞書の掲載順だけを使用頻度の証明にせず、誤りがあれば独立した根拠に基づく正本修正を先に行う。同綴り異義語の語根IDは保持する。

## 担当1：語義を確認してプロンプトCSVを作る

2. 日本語 `語義` は代表的な順に整えた正本の値を保持する。`対象語義` はその先頭と同じ表現にする。英語欄の空欄だけで画像化を保留しないが、正本の第一英語義は空欄も含め正確に記録する
3. 正本の見出し語・語根ID配列・第一日本語義・第一英語義から `語義SHA256` を記録する。定義は正本の `tools/illustration_scenes.py` の `first_senses` / `sense_digest`。自己流の区切り・配列並べ替えを使わない。初回の取り込みに備え、引き渡し時の反映先PNG・解説・原本レコードのハッシュを既存の実行記録／反映manifestへ控える
4. 同じ語の画像でも意味が違えば再利用しない。再利用候補は実物と意味を確認する。通常画像は代表的な第一語義。追加語義は既存の複数画像処理と命名規則を確認し、独自の連番・接尾辞を作らない
5. 具体物は直接、抽象語は具体的な行動・状態・関係で表す。人名・地名も対象にするが、大文字始まりだけで人物化しない。分からない固有名詞の人物像や特徴を事実として捏造しない
6. `画像生成プロンプト` を Subject / Composition / Style / Framing / Output の5項目、サンプル程度の文量（英語約100語）で作る。共通の保存・検品手順や長い禁止事項一覧を各プロンプトへ重複記載しない
7. 全行で `対象語義` と Composition の意味を照合し、完了した行だけ `プロンプト準備状況=作成済み`、未解決なら `要確認` と理由を記録する。実行プロンプト・実画像ハッシュ・検品日時はまだ空欄。準備済みの行だけ `制作状態=prompt_ready` とし、要確認行は `needs_revision`

解説は担当2が採用実PNGを見て確定する。担当1が草稿を置く場合も未検品であることを明記し、プロンプトだけで `reviewed` にしない。

## 内容設計
**何を描くかはプロンプト本文で決める。参照画像に内容を決めさせない。**

### Composition の具体性は必須
- Composition は、**その英文だけを画像生成担当へ渡しても、何を描けばよいか一意に近く判断できる**ところまで具体化する。
- 見出し語や語義を言い換えただけの指示はプロンプトとして認めない。
- 次のような丸投げ表現は禁止する。
  - `Show a visual example of X.`
  - `Show a concrete example of X.`
  - `Show a subject representing X.`
  - `Show a person matching X.`
  - `Show a plausible person representing X.`
  - `Show a natural scene of X.`
  - 「適切な物・人物・場面を描く」のように、描く対象を生成AI側へ選ばせる文
- 抽象語・形容詞・副詞でも、必ず**具体的な物体・人物・行動・表情・状態・位置関係**へ落とす。
- 例：`acidic / 酸っぱい` → 半分に切ったレモンを一口かじった人物。目を細め、頬と口元を強くすぼめて酸味に反応している。片手に切ったレモンを持たせる。
- 例：`careful / 注意深い` → 両手でガラスの器を支え、足元を確かめながらゆっくり運ぶ人物。慎重な持ち方と姿勢を見せる。
- 例：`narrow / 狭い` → 二つの壁の間に、人が横向きでやっと通れる細い通路を描く。
- **「語義を消した Composition を読んでも具体的な絵が想像できるか」**を完成判定に使う。できなければ作成済みにしない。

必要に応じて以下を具体化する。
- 主役
- 人物の年齢・性別・職業
- 表情
- 行動
- 小物
- 食べ物・飲み物
- 器
- 温度
- 調理状態
- 位置関係

### 主役・人物の選び方
- 語義が最も直接伝わる主役を、人物・物体・動物・食べ物・道具・自然物などから選ぶ。
- 人物を使う場合は、語義に合う人数・年齢・性別・職業・表情・行動にする。
- 例：`I` は1人が自分の胸を指す。
- なるべく最小構成を目指す

## 参照画像の使い方
- 参照画像は **1語につき必ず1枚だけ**。
- 使用する参照画像は **常に `references/invidious.png`**。
- 複数参照は禁止。

参照するもの：
- 太く丸い濃茶色の輪郭
- 単純化した丸みのある2D形状
- 明快な読みやすさ
- 控えめなカートゥーン陰影
- **人物が必要な場合の標準キャストの顔立ち・頭身・親しみやすさ**

参照しないもの：
- 単語の主題
- 小物
- 場面
- 構図
- 参照画像に偶然描かれている植物・料理・道具など

---

## 画風
- 太く丸い濃茶色の輪郭
- 強く単純化した2D形状
- 明快で読みやすいシルエット
- 控えめなカートゥーン陰影
- 写実・3D・細密画にはしない
- 人物の感情は眉・口・姿勢などで語義に合わせる
- 人物の年齢や体格は語義に応じて変える

---

## 構図
- 1画像1構図。
- コラージュ・一覧・比較図は禁止。
- 主役は大きく、長辺80〜90%程度を目安にする。
- 関連する人物・小物は、意味が読みやすい位置関係にする。
- 大きな空白帯を作らない。
- 手足・道具の先端は切らない。
- 無機質なピクトグラムにならないよう、必要な場面・感情・関係を持たせる。
- 意味に不要な背景や物語は増やさない。

## 文字・数字・記号が語義そのものの場合
通常のイラストでは、意味に不要な文字・英単語・数字・ラベルを入れない。

**台詞・説明文を画像内に書いて意味を説明しない。** 文法語・抽象語・人物属性でも、文脈例文や自己紹介を台詞にして補う方法は禁止。空の吹き出しに置き換えて済ませず、指差し・動作・表情・所有関係・物理的な結果などの具体的な非文字場面を設計する。

画像単独のクイズで綴りや活用形を一意に当てられないことと、語義の場面例を描けないことは区別する。妥当な場面例が作れる語は一律に保留しない。どうしても誤った意味になる場合だけ、理由を明記して要確認とし、作成済みに偽装しない。

ただし、**文字・文字体系・句読点・記号・数式など、その視覚的な表記自体が対象物である場合は例外**とし、その対象を描くために必要な最小限の文字・数字・記号だけを使う。時刻・数量・数式・化学式などの本質的な表記と、語義を解説する台詞・説明ラベルは区別する。文法を例文で説明する目的ではこの例外を使わない。

例：
- kanji.png → 「山」「川」「日」「人」など複数の代表的な漢字を描く
- katakana.png → 「ア」「イ」「ウ」「エ」「オ」など複数の片仮名を描く

この例外でも、**見出し語そのものを答えとして書くだけの画像にはしない**。
たとえば `kanji` や「漢字」とだけ書いて済ませず、実際の漢字の例を描く。

文章・記事・詩などを物体として描く場合は、原則として読めない紙面の行や筆跡で表現する。語義を言い換えた説明文、見出し語の表示、台詞を添えて答えにしない。文字そのものが対象となる場合の最小限の実例は、上の例外に従って個別に確認する。

## 出力仕様
プロンプトのOutputはサンプルに準拠する。完成画像は1語1枚、512×512 PNG・RGBA・実アルファ透過（背景・外周・空隙）。市松模様・白背景・色背景・ロゴ・透かし・不要な文字やラベルは禁止。文字使用の例外は前節に従う。

## 語義とCompositionの意味一致チェック
- **最終判定は英単語の綴りや大文字小文字ではなく、日本語の `対象語義` を基準にする。**
- 大文字で始まる語を、人名・都市名・国名などへ自動分類してはいけない。**大文字始まりは分類根拠にしない。**
- 人物を描く Composition にするのは、`対象語義` が実際に人名・人物・職業・人物属性を表す場合だけ。
- 曜日・月・国・都市・地域・宗教・団体・学術用語・天体・物質・抽象概念などを、見出し語が大文字だからという理由だけで人物化しない。
- 例：`Saturday / 土曜日` → 「Saturdayという名前の人物」は不合格。土曜日そのものを表す週末・カレンダー等の具体構図にする。
- 例：`Italian / イタリアの` → 「Italianという名前の人物」は不合格。イタリア性が読める地理・建築・文化的手掛かりで構成する。
- 例：`Jerusalem / イェルザレム` → 人物ではなく都市として描く。
- 例：`Jupiter / 木星` → 人物ではなく惑星として描く。
- Composition が具体的で文法的に正しくても、**対象語義と主役・場面が一致しなければ不合格**。
- 完成判定では各行について、`対象語義` と `Composition` を必ず並べて読み、**「このCompositionから対象語義が自然に読めるか」**を確認する。
- 禁止テンプレ検索だけで納品判定を終えない。既知パターンに引っかからない意味不一致もあるため、**全行で意味照合を行う。**
- 迷う場合は英語見出しから意味を推測せず、日本語の語義と辞書本文へ戻る。


## CSV仕様：既存7列を保持し、末尾へ追加する

文字コードはUTF-8（従来どおりBOM可）。カンマ・引用符・改行はCSVライブラリでエスケープする。物理行番号ではなくCSVレコードで扱う。

先頭7列は従来と同じ順：

`ファイル名,語義,対象語義,画像生成プロンプト,プロンプト準備状況,要確認理由,画風参照画像`

追加12列は以下の順。旧CSVの空欄は「未確認」であり、完了を意味しない。サンプルの追加列は未記入の書式例で、原本へ取り込む実制作レコードではない。新規制作では担当1が正本から識別情報を埋める。

| 列 | 記録する内容・担当 |
|---|---|
| 単語 | 正本の正確な見出し語。担当1が記録、担当2は推測で変更しない |
| 語根ID_JSON | 正本 `p` の順序を保ったJSON配列。根なしは `[]`。根をソートしない |
| 第一英語義 | 正本の第一英語義。`語義SHA256` の計算に使った値 |
| 語義SHA256 | `sense_digest(単語, 語根ID配列, 対象語義, 第一英語義)`。原本変化の検出用 |
| 実行プロンプト | 担当2が実際に画像生成へ送った全文。変更なしでも全文を記録する |
| 解説英語 | 採用実PNGを見た短い英語解説。ラベルを前置しない |
| 解説日本語 | 同じ場面を自然に説明する短い日本語。ラベルを前置しない |
| 制作状態 | 下記の工程状態。既存のプロンプト準備状況とは別 |
| 画像SHA256 | 実際に検品した最終PNGバイト列のSHA256 |
| 画像GitBlobSHA | 同PNGのGit blob SHA1。コミットSHAとは別 |
| 検品日時 | 実PNGと両解説を確認した日時。タイムゾーン付きISO 8601 |
| 検品メモ | 実PNGの確認方法、語義との対応根拠、解説確認。失敗・修正待ち・記録欠落も具体的に残す |

`画像生成プロンプト` は担当1の引き渡し案として保持し、`実行プロンプト` に実送信した内容を残す。生成時に構図を改善した場合も、チャットだけで済ませずCSVへ保存する。再試行では現在の画像に対応する実行プロンプトを記録し、前回の内容と失敗理由はGit履歴または既存の実行記録で追跡可能にする。

機械的な行の識別キーは `(単語, 順序付き語根ID配列, ファイル名)`。単語だけ・ファイル名から推測した語根だけで結合しない。旧行を補うとき、作業一覧との対応が一意に確認できなければその行を保留する。

### 工程状態

- `prompt_ready`：プロンプト準備済み。画像未確認
- `generated`：生成結果を保存し、要求と行の対応を記録済み。まだ検品合格ではない
- `reviewed`：第一語義・採用PNG・英日解説・数値仕様の全検品に合格し、ハッシュと根拠を保存済み
- `applied`：検品した組が辞書原本へ反映済み。公開済みかどうかは反映manifestで別途記録する
- `needs_revision`：語義・画像・解説の不整合または検品不合格。理由と次の修正を残す
- `error`：生成・保存・読込などの実行失敗。`要確認理由` に短い原因、`検品メモ` に再開に必要な情報を残す

`generated` と `reviewed` と `applied` を混同しない。語義・PNG・解説・実行プロンプトを変更したら、その影響を受ける検品と適用状態を戻す。修正待ちの行だけを止め、独立して合格した行は先へ進める。

## 担当2：生成・検品・解説追加・CSV更新

1. 自分の担当CSVの現在位置を確認する。生成対象は準備済みかつ実PNG未確認の行。既にあるPNGは再生成の前に実物・対応記録を調べる
2. 1回の要求は1行・1語・1画像。グリッド・一覧・複数パネルを作って切り分けない。CSVの指示を使い、唯一の画風参照を実際に添付する
3. 生成要求を出す前に行キーと実行プロンプトを固定する。その要求から返った結果パス／結果IDと行キーの対応を、同じ処理の実行記録に残す
4. 生成完了順・時刻・フォルダ順・画像の見た目から行への割り当てを推測しない。失敗行を前後の生成物で穴埋めしない。中断で対応を復元できない生成物は採用しない
5. `実行プロンプト` に実際の全文を保存する。出力とファイル名を照合してステージングへ保存し、`generated` にする。生成案を後から変更しただけで既存画像のプロンプトを更新したことにしない
6. 以下の数値・目視検品を全件行う。実PNGを見て短い英日解説を書き、後述の品質基準で両文を読み直す。語義に合わなければ画像を直し、説明で言いくるめない
7. 最終PNGの両ハッシュ、検品日時・根拠を記録し、全条件を満たした行だけ `reviewed` にする。実PNGを見ていない状態やCSV編集だけで検品済みにしない
8. 1件ごとにCSVを安全に保存する（同一フォルダの一時ファイルを書き、読み戻し検証して置換）。バッチ末まで記録を溜めない。同じCSVを複数担当者が同時に保存しない

`work/etymopedia/_illust` は従来の検品合格画像のステージング先。未検品候補はそこから区別し、現在の担当別保存構成を変えない。同名ファイルの存在だけで生成・検品・原本反映を完了扱いにしない。

## 生成後の数値検品
各PNGについて最低限確認する。
- 512×512であること
- PNGであること
- RGBAであること
- 実際のアルファチャンネルが存在すること
- 背景が透明であること
- 市松模様を画像として描き込んでいないこと
- ファイル名がCSV指定と完全一致すること
- 一覧画像になっていないこと

## 生成後の目視検品
生成画像を以下の背景に重ねて確認する。
- 白背景
- 濃紺背景
- ピンク背景

目視で確認する。
- 白い縁取りや色にじみがないか
- 背景が本当に透過しているか
- 主役や手足・道具が見切れていないか
- 不要な文字・数字・ラベル・ロゴ・透かしが入っていないか（対象物そのものの最小限表記は既存の例外を確認）
- 語義と違うものを描いていないか
- 参照画像の主題・小物・構図をコピーしていないか
- 同じ不要モチーフが大量に反復していないか
- 人物の年齢・体格・職業がCompositionの指定と合っているか

問題がある画像は採用せず、該当行の実行プロンプトを修正して再生成する。語義は絵を救うために変更しない。


## 解説の品質をそろえる：短く、具体的に、自然に

英語・日本語とも短い句または一文。説明を画像の外へ表示するための本文だけをCSVに保存し、`イラスト解説：`、`English:`、見出し語ラベルなどは付けない。

- **英語は通常6〜14語程度を目安、上限18語。最低語数は設けない。** 単純な物や状態は3〜5語程度の自然な句・文でもよい。短いことだけで不合格にせず、必要な情報があるかを確認する
- 英語には正本の見出し語の正確な形を自然に含める。大小文字など既存validatorの正規化は可。見出しが `taken` なら `take` だけへ置き換えない。現行validatorは別の活用形だけでは通らないため、規則を拡張したとみなさない
- 日本語は同じ場面を短い句または一文で表す。通常15〜35字程度を目安に読み直すが、機械的な最低字数・直訳・水増しはしない。英語にない断定や物語を足さない
- 具体物は主役＋見える特徴または状態を一つ。動作・抽象語は誰／何がどうしているか、または物の関係と語義のつながりを必要なだけ書く
- 辞書の一般定義を丸写しせず、この絵の具体的な情報を持たせる。`This is X.`、見出し語だけ、循環定義の量産は禁止
- 長い背景説明、言い換えの重複、画風・色・小物の不要な列挙は削る。見えていない動機・過去・未来・固有名・診断を推測で追加しない
- 抽象語は画像・語義・解説を一緒に読んで意味が自然に通ることが基準。画像だけでは一意に当てられないことを理由に、余分な筋書きや画像内の文字を足さない

### 良い例と直す例

例は、その特徴が実画像に描かれている場合に限る。全行へ固定文型を流用しない。

| 場面 | 良い英語／日本語 | 直す例・理由 |
|---|---|---|
| 開いた木のドア | The wooden door is open. ／ 木のドアが開いている。 | This is a door. は絵の特徴がない。短さを埋めるために部屋の歴史などを足さない |
| 丸い風船 | A round balloon. ／ 丸い風船。 | Balloon. は名を繰り返すだけ。単純な具体物なので3語でも無理に増やさない |
| おもりがスポンジを押しつぶす | The heavy weight puts pressure on the sponge and squashes it. ／ 重いおもりがスポンジに圧力をかけ、押しつぶしている。 | Pressure means pressure. は循環定義。見えていない仕事のストレスの話を足すと別の意味になる |
| 列から脇道へそれる人 | They deviate from the line onto a side path. ／ 列を離れ、脇道へそれている。 | They deviate. だけではどこからどう外れたのか不足。「退屈だから」など見えない理由を足さない |

### 各行の解説チェック

1. 第一語義と品詞・見出し語の形に合うか
2. 実画像の主役・特徴・行動・関係のいずれかを具体的に説明しているか
3. 英語は自然で18語以内か。短すぎる候補は情報不足を点検し、語数だけを理由に水増ししない
4. 日本語は同じ内容で自然か。長い修飾や解説の重複を削ったか
5. 見えない事実・循環定義・定型句の繰り返しで不整合を隠していないか

英語語数は正本 `tools/illustration_scenes.py` の `english_word_count` と同じ数え方を使う。NFKC等を正規化した後、内部のアポストロフィ・ハイフンを含む語は1語として数える（例：`don't`、`snow-capped`）。独自の空白分割で別の判定にしない。

自動確認では18語超・見出し語欠落・空欄・複数文・名だけの文を止める。6語未満や日本語の目安外は読み直し候補であり自動不合格ではない。冗長さ・意味の薄さ・見えない内容の混入は実物との目視照合で判定する。担当2は各行に加えてバッチ内の完成解説を通読し、特定の文型や過剰な長短が続いていないかも確認する。

## 既存画像への解説追加は別の作業として進める

- 新規画像生成を待たず、現行PNGを確認できる生成・採用済み画像の欠けた解説をレア度順に補う
- 既存PNGを実際に開き、現在の第一語義と三者整合を確認する。語義・画像が不一致ならその行だけ `needs_revision`
- 実行プロンプトが不明な過去画像は空欄のまま「既存画像への解説追加・実行プロンプト不明」と記録する。画像を見て過去のプロンプトを逆算・捏造しない
- その場合の反映は解説だけ。PNGを書き換えたり、画像生成数・Git画像更新日を増やしたりしない。新規生成行での実行プロンプト欠落は修正するまで反映対象外
- 対応CSVがある場合は担当者が該当行へ追記する。過去画像のためだけに重複した新規生成CSVを作らず、既存の正本解説台帳と反映記録を使う

## 反映バッチ：検品した画像・解説を原本へ取り込む

### 反映先と対応

画像は従来の正式パス `assets/word/<ファイル名>` へ。解説の唯一の正本は非公開 `etymon-source/app/data/pie/word_illustration_scenes.json`。既存のschema 1を使い、語義・読み・語源・タグ・メモへ解説を上書きしない。

- `w` ← `単語`
- `p` ← `語根ID_JSON` を配列として読んだ値（順序維持）
- `art` ← `ファイル名` の末尾 `.png` のみを除いた値
- `sense` ← `{index: 0, ja: 対象語義, en: 第一英語義, sha256: 語義SHA256}`
- `scene` ← `{en: 解説英語, ja: 解説日本語}`
- `image` ← `{path: assets/word/<ファイル名>, sha256: 画像SHA256, git_blob_sha: 画像GitBlobSHA}`
- `review` ← `{status: reviewed, reviewed_at: 検品日時, method: 実際の確認方法, notes: 検品メモ}`。`method` を機械的に検品済みと捏造しない

### 安全な差分反映と再開

1. `reviewed` 行だけを候補にする。行キーの重複、必須値不足、未検品、実行プロンプトの欠落（既存画像への解説追加を除く）、PNG形式／ハッシュ不一致はその行をスキップし、理由を残す
2. 最新原本の同じ `(w, p)` を引き、正式画像との対応・第一語義を確認する。現在の `sense_digest` とCSVの `語義SHA256` が違えば競合としてスキップする。古いCSVで新しい語義を上書きしない
3. 反映前に現在のPNGと原本解説のハッシュを確認する。既存の反映manifestにある直前の適用値と違う場合、別作業の更新を上書きせず競合にする。初回は引き渡し時、または担当2が現在の原本・PNGを確認して作業を再開する時点の値（存在しなければ明示的なnull）を基準として記録し、書込直前にも再確認する。基準記録がなく既存データを置換する場合は自動反映せず、その行の現行内容を改めて確認する
4. 同じキー・語義・画像ハッシュ・解説ハッシュの組が既に適用済みなら何もしない。同名画像だけ、状態名だけで重複判定しない
5. 合格したPNGと対応する正本解説を一組でステージし、既存validatorで検証する。画像の切り替え前後で古い解説と新画像を混ぜない。1行の失敗で独立した合格行まで取り消さないが、公開書出しの検証が失敗したら公開は止める
6. 正本への保存と読み戻し確認が成功した行だけ `applied`。公開データ・画像の遠隔確認が完了した時点はmanifestに別途記録する。複数リポジトリを一つの原子的コミットだと扱わない
7. 中断後はmanifestの段階と実データを照合して再開する。原本保存済み・公開待ちの行は公開工程から再開し、再生成や原本の二重適用をしない

反映manifestは、再実行と競合防止に必要なバッチの機械記録1つとする。似た監査CSVを増やさない。新しい取り込み処理が保存すべき最小項目は、CSVパスと読み込んだSHA256、行キー、語義SHA256、反映前の画像／解説ハッシュ、最後に適用した画像SHA256・解説SHA256、原本反映／公開の段階、コミットSHA、成功・スキップ理由。解説ハッシュは正本の `normalize` を各文に適用した `[en, ja]` のコンパクトUTF-8 JSONをSHA256とする。既存の反映manifestがある場合はそれを拡張して使う。

解説だけでなく他の担当者の検品記録を守るため、原本側の該当レコード全体の反映前ハッシュも比較する。画像・解説本文が同じでも別担当の更新があれば確認してから取り込む。manifestは成功した後だけ更新し、失敗を適用済みに偽装しない。
